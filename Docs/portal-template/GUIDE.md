# Adoption and design guide

This guide answers two questions the README deliberately leaves out: **should you use this template**, and **why is it built this way**. For installation and deployment commands, see [`README.md`](README.md). For how to change the template itself, see [`CONTRIBUTING.md`](CONTRIBUTING.md).

## When to use this template

Reach for this template when a project needs **versioned architecture documentation with diagrams that stay in sync with the text**.

It is a good fit when you need:

- **Versioned architecture docs.** Multiple documentation snapshots — Latest, a frozen release, and a forward-looking preview — served side by side, with a version switcher. Readers on an older release see the docs that match the code they are running.
- **C4 diagram integration.** Architecture models authored as text in LikeC4, compiled at build time, and rendered as interactive pannable/zoomable diagrams whose nodes link to the pages that describe them. Diagrams live in version control and review as diffs, not as binary exports.
- **Multi-snapshot documentation.** Each version carries its own content tree *and* its own architecture model, so a historical page never silently shows today's architecture.
- **Static hosting with search.** Fully static output with a Pagefind full-text index, deployable to GitHub Pages at either a domain root or a `/repository-name` subpath.
- **Build-time guarantees.** Malformed diagram models, missing routes, and broken internal links fail the build rather than reaching readers.

It is a poor fit when:

- You need a **single unversioned docs site**. The three-version structure is the template's core shape; stripping it out leaves plain Starlight, which you should start from directly.
- Your documentation is **prose-only**, with no architecture model. The LikeC4 toolchain is most of the build cost and all of the complexity budget.
- You need **runtime content** — search over a database, authenticated pages, per-user views. The output is static files.
- You want **automatic navigation from the filesystem**. Sidebars here are written by hand, on purpose. See below.

## Design philosophy

Three choices in this template look like extra work. Each is deliberate, and each trades authoring convenience for a property that matters more in versioned documentation.

### Manual sidebars over auto-generation

Sidebars are declared explicitly in `astro.config.mjs` for Latest and in `src/content/versions/*.json` for each frozen version, rather than generated by walking `src/content/docs/`.

**Why:** Auto-generated navigation makes the sidebar a function of the filesystem, so adding a file silently changes the reading order of a published version. In versioned documentation that is a correctness problem — a frozen snapshot's navigation must not shift because someone added a page to Latest. Explicit sidebars also let reading order differ from directory structure, and make navigation changes reviewable as a diff.

**Cost:** Every new page needs a sidebar entry, and a forgotten entry means an unreachable page. The route validator catches the inverse (a sidebar entry with no page); it does not catch an orphaned file.

### Duplicated version snapshots over dynamic queries

Each version is a complete independent copy: `src/content/docs/v1/` holds full copies of every page, not diffs or references to Latest, and `likec4/v1/` holds a full model.

**Why:** A frozen version must stay frozen. If historical pages resolved shared content at build time, an edit to Latest would rewrite the documented history of a shipped release. Duplication makes each snapshot immutable by construction — you can only change v1 by editing files under `v1/`. It also keeps every page trivially readable on its own, with no indirection to follow.

**Cost:** Fixing a typo that exists in all three versions means three edits, and the repository grows linearly with version count. This is the intended trade: snapshots are meant to be written once and then left alone. Do not add tooling that "propagates" a fix into a frozen version — that reintroduces exactly the mutability this design removes.

### Literal engine imports over runtime discovery

`src/components/DiagramView.tsx` maps project names to imports in an explicit object literal:

```ts
const ENGINE_BY_PROJECT = {
  current: () => import('likec4:react/current'),
  v1: () => import('likec4:react/v1'),
  preview: () => import('likec4:react/preview'),
};
```

**Why:** The `likec4:react/*` specifiers are virtual modules resolved by the LikeC4 Vite plugin at build time. A computed specifier such as `` import(`likec4:react/${project}`) `` cannot be statically analyzed, so the bundler cannot resolve or code-split it. Listing each project literally is what makes per-version diagram engines lazy-loadable as separate chunks — a reader on v1 never downloads the Latest or Preview engine. It also turns an unknown project name into an explicit error instead of a silent fallback to Latest, which would show the wrong architecture without saying so.

**Cost:** Adding a version means editing this map. That edit is on the version checklist below.

### Supporting choices

- **Normal links beside every diagram.** Architecture pages carry ordinary HTML links to the same pages the diagram nodes point at, so navigation survives with JavaScript disabled and works for keyboard and screen-reader users. Diagram nodes are an enhancement, never the only route.
- **Unmapped nodes stay native.** The click handler only intercepts nodes present in `nodeLinks`; everything else keeps LikeC4's own pan, zoom, and drill-down behavior.
- **`throwIfInvalid: true`.** An invalid model fails the build rather than rendering a blank or stale diagram.
- **Base path applied once, at the edge.** `src/rehype-base-links.mjs` rewrites root-absolute authored links exactly once under `BASE_PATH`, leaving relative links, anchors, external URLs, and protocol-relative URLs untouched. Authors write `/features/example-feature` and never think about deployment path.

## Customization patterns

### Replacing the sample content

1. Set `title` and `description` in the `starlight({ ... })` block in `astro.config.mjs`.
2. Replace the four Latest pages under `src/content/docs/`: `index.md`, `architecture.mdx`, `features/example-feature.md`, and `decisions/0001-static-documentation.md`.
3. Update the `sidebar` array in `astro.config.mjs` to match your page slugs.
4. Replace `public/favicon.svg`.
5. Repeat steps 2–3 for `v1/` and `preview/`, updating `src/content/versions/v1.json` and `preview.json`.

Keep the shape — index, architecture, at least one feature, at least one ADR — until you have a reason to change it. The route validator in `scripts/validate-site.mjs` expects twelve routes; if you change the page set, update that list in the same commit.

### Adding a version

Adding `v2` touches seven places. Missing any one of them produces either a build failure or a version that silently renders another version's diagrams:

1. Copy the Latest pages to `src/content/docs/v2/`.
2. Create `src/content/versions/v2.json` with that snapshot's sidebar.
3. Register `{ slug: 'v2', label: 'v2' }` in `starlightVersions()` in `astro.config.mjs`.
4. Copy a LikeC4 project to `likec4/v2/` and set `name` in its `likec4.config.json`.
5. Add a literal `v2: () => import('likec4:react/v2')` entry to `ENGINE_BY_PROJECT` in `DiagramView.tsx`.
6. Pass matching `project`, `label`, and version-prefixed `nodeLinks` from the v2 architecture page.
7. Add the four `v2` routes to the required-route list in `scripts/validate-site.mjs`.

Then run both verification commands. Never make a historical page pull in Latest content.

### Customizing LikeC4 models

Each directory under `likec4/` is an independent project with a `model.c4` and a `likec4.config.json`. Edit the model in place; the `viewId` passed from an architecture page must match a view declared in that project's model. Because `throwIfInvalid` is on, a typo in an element reference fails the build with the offending file named.

To link diagram nodes to pages, pass a `nodeLinks` map from the architecture page keyed by fully qualified LikeC4 node ID, with values as authored routes. Node IDs must be fully qualified, and routes must be version-correct — a v1 diagram should link to `/v1/features/...`, not `/features/...`.

### Configuring base paths

`astro.config.mjs` reads two environment variables:

| Variable | Purpose | Local default |
| --- | --- | --- |
| `SITE_URL` | Canonical origin, without project path | `http://localhost:4321` |
| `BASE_PATH` | Hosting path: `/` or `/repository-name` | `/` |

Use `/` for user, organization, and custom-domain sites. Use `/repository-name` for GitHub project sites. Verify both shapes before deploying — `npm run verify:root` and `npm run verify:subpath` exist precisely because base-path bugs are invisible in local root-hosted development.

### Adding GitHub Pages variables

The bundled `.github/workflows/pages.yml` reads `SITE_URL` and `BASE_PATH` as **repository variables**, not secrets, so it carries no hardcoded organization or repository name:

```bash
gh variable set SITE_URL --body "https://your-org.github.io"
gh variable set BASE_PATH --body "/your-repo"
```

Then set **Settings → Pages → Source** to **GitHub Actions**. Set the variables *before* the first push to `main`, or the first deploy publishes a site with wrong canonical URLs.

## Adopting via "Use this template"

Creating a repository from this template gives you a squashed single-commit copy with **no upstream link**. You will not receive later fixes automatically, and there is no merge path back. Updating means re-copying the changed files by hand and re-running both verification commands.

This is the expected trade for a scaffold: you own your copy outright and can diverge freely from day one. If you want to track upstream changes, watch this repository's `CHANGELOG.md` and port entries deliberately.

## Production example

The VNRacing project documentation portal at `Click-Game-Studio/VNRacing` (`Docs/portal/`) runs the same architecture — Starlight, versioned snapshots, and LikeC4 diagrams — against a game-development domain rather than the neutral sample content shipped here. It is a useful reference for what the structure looks like once real content, a real architecture model, and a real version history fill it in.
